# CLAUDE.md

`unsent` is AutoRecover for AI agent prompts: a Go wrapper that runs an agent CLI in a pseudo-terminal and keeps the text in its input box saved on disk.

## Layout

## Facts about Claude Code's box (measured on 2.1.282)

- Drawn between two full-width `─` rules; the first row starts with `❯` plus a no-break space (U+00A0), shell mode with `!`.
- A named session's top rule carries its name at the right end, in the rule's colour: `──…── calls ─` (`claudeTitledRule`), from the `/rename` that names it on, and from the first frame of a session resumed by name; at any width the rule stays full width: a name as wide as the window minus three leaves no `─` before it (` name ─`), and a wider one is cut with an ellipsis (` nam… ─`). The name never shows in the box row. Measured on 2.1.284, and 2.1.282 and 2.1.283 draw it too. Up to v0.6.0 the reader took only a plain rule, so after `/rename` it lost the box for the rest of the run. The `/rename` line was left behind as an orphan, nothing typed later was saved, and the exit printed nothing, because the box had been read once. History browsing's label sits at the left end (`─── History 1/1 ───…`) and still means the box is not read (docs/research/claude.md section 13).
- An empty box shows the marker, then Claude Code's own cursor, a reverse-video space. A configured install also shows a dim (SGR 2) `Try "…"` hint there; a clean config shows none. Nothing but spaces or dim text after the marker is how an empty box is told apart from a draft. ← on an empty box opens the agents view, whose box between dim rules shows the placeholder `❯ describe a task for a new session` with the marker and the text in one grey (`38;5;246`, not SGR 2) and the reverse-video cursor on the first letter; `claudePlaceholder` reads that as empty (the main box draws its marker and typed text in the default colour). Opening that view starts a Claude Code background daemon and a forked `--resume` session outside unsent's terminal, which outlive the run.
- Rows wrap at window width minus 4 columns; a word longer than that breaks at exactly that width, or one column short when a wide character would cross the edge, and it can start mid-row after other words.
- The box stops growing at `rows/2 - 5` rows and then scrolls; the `❯` marks the first visible row, not the first row of the draft.
- The real terminal cursor sits at the insertion point.
- Up moves the cursor row by row until it reaches the middle row of a scrolled box; each Up after that scrolls the box one row and the cursor stays mid-box, until the first row of the draft is in view. ## Facts about zsh's line editor (measured on 5.9)

- `line-pre-redraw` fires before each redraw, never for a fresh prompt, and zsh skips it while more input is pending: keys sent in one write with a Ctrl+C may get no redraw at all.
- `line-init` fires at every prompt, after Ctrl+C too, with `$CONTEXT` `start`, or `cont` at a continuation prompt. `line-finish` fires on every Enter, including one that only opens a continuation prompt (`echo "a`), so a finish is a send only when no `cont` init follows it.
- vared runs the same hooks with `$CONTEXT` `vared`; `read -s` never starts the line editor.
- `add-zle-hook-widget` keeps each hook's widgets as `<n>:<widget>` in the `widgets` style of context `zle-<hook>` (a `zle-<hook>` widget defined directly becomes `0:user:<name>`), runs them in number order and stops at the first that returns non-zero, so a user's failing hook added before ours kept ours from running. The block gives its widgets 0 and moves the others up by 1; a widget added later gets the highest number plus 1. Loaded without zsh emulation, the dispatcher fails under `sh_glob` for every widget.
- Inside `TRAPHUP`, `$BUFFER` and `$CONTEXT` hold the prompt's line, and `zle` with no arguments returns 0; during `read -s` or a running command `$CONTEXT` is unset and `zle` returns 1. A `TRAPHUP` that returns keeps the shell running; `unfunction TRAPHUP; kill -HUP $$` exits as the default does and hangs up the jobs.
- Ctrl+C drops input still queued in the terminal (seen on Linux), so a test waits for the next prompt before typing again.
- A Ctrl+C that arrives while the line editor is busy (a redraw, a hook) takes effect only when the next key arrives, and that key is dropped. Seen on Linux under load, in plain zsh too; the hooks' write on every key makes it more likely. A test that waits for the prompt after Ctrl+C sends a Backspace now and then, which is dropped behind a pending Ctrl+C and does nothing at an empty prompt.
- The prompt shows before `line-init` runs; zle prints `ESC[?2004h` (bracketed paste on) after it, so a test waits for that before it relies on the hook. Keys typed while a command runs, or before the first prompt, are echoed by the terminal itself, not by zle, and zsh on macOS can lose a line typed before its first prompt.
- Defining a `TRAPHUP` function replaces a list-form `trap '...' HUP`, an empty one that ignores HUP included. `$(trap)` prints nothing, since a command substitution's subshell has no traps; `trap >file` lists them without a fork.
- A trap set inside a function under `emulate -L zsh` is undone when the function returns (`local_traps`), unless the function sets `no_local_traps` first.
- The same goes for a trap removed there. A signal that comes while a function under `emulate -L` runs, nested deeper than where the trap was set, runs the trap inside it; a `TRAPHUP` that does `unfunction TRAPHUP; kill -HUP` is put back when it returns and runs again for its own signal, forever. `setopt local_options no_local_traps` as the trap's first line keeps it removed, for an `unfunction` in a user's `TRAPHUP` it calls too, since that function inherits the options.
- Under `no_hash_list_all`, `${+commands[x]}` is 0 for a command on `PATH` that zsh has not hashed yet, inside `emulate -L zsh` too (plain `emulate` does not reset that option). `whence -p x` searches `PATH` and is a builtin.
- A subshell waiting on an external command such as `sleep` runs its traps only after the command ends; one waiting in the `zselect` builtin runs them at once.
- While Up or Ctrl+R shows a history entry, `$HISTNO` is that entry's number and `${history[$HISTNO]}` its text, which an edit to the buffer does not change; at a new line `$HISTNO` equals `$HISTCMD`. `HISTORY_IGNORE` filters only the history file, so an ignored line can still be recalled.
- In the C locale `${#x}` counts bytes whatever `multibyte` says, so a test of byte counts needs a UTF-8 locale (`C.UTF-8` on Linux, `en_US.UTF-8` on macOS).

## Rules

- Tests: `go test -race ./...`. Coverage target 90% (`codecov.yml`).
- `wrap_test.go` re-runs the test binary as a fake agent; keep it drawing the box the way the real one does.
- `shell_test.go` runs the hooks in a real `zsh -f -i` on a pseudo-terminal under an empty environment with a scratch `HOME` and `ZDOTDIR`, types at it and reads the log's records; `testdata/shell/zsh-init.golden` pins what `unsent init zsh` prints (`UNSENT_UPDATE_GOLDEN=1` rewrites it). Its waits end on progress, not on a total: one fails after 20 s with nothing new on the terminal or in the logs (a minute before the first prompt), or after 3 minutes in all, and prints what it saw; a loaded shared runner can take a second over each key. Waiting for a shell to exit after a signal is bounded in total, because a shell that keeps writing after its hangup is the failure. A wait for something a hook writes before a redraw also ends once zsh has drawn past that point (`takes`, `minesRan`), so a mutated copy fails at once instead of after the 20 s stall. Keep the mutation tests red: without the `i` mark a Ctrl+C runs into the next line, without the `$CONTEXT` check vared text is saved; the HUP-trap, deep-hook hangup, failed-write, folder-owner and UTF-8 tests each run a mutated copy of the hooks that must go red, and so does `TestZshHooksLetTheUsersHooksRun` for each of our widgets returning non-zero (no `unsent` on `PATH`, a cursor move), since the dispatcher then skips the user's hooks.
